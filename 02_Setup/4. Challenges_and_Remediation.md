# Wazuh Installation — Challenges Faced & Remediation

## Overview

This document covers the real-world challenges encountered during the installation of Wazuh 4.14.x (all-in-one deployment) on an Ubuntu 24.04 VM running on VirtualBox with a Bridged network adapter, and the steps taken to diagnose and resolve each issue.

---

## Environment

| Component        | Details                                      |
|------------------|----------------------------------------------|
| Host OS          | Windows 11                                   |
| VM Software      | VirtualBox                                   |
| Guest OS         | Ubuntu 24.04 LTS                             |
| Network Mode     | Bridged Adapter (MediaTek Wi-Fi 6E MT7902)   |
| ISP              | Jio (Ahmedabad, India)                       |
| Wazuh Version    | 4.14.5 / 4.14.6                              |
| Install Method   | `wazuh-install.sh -a` (all-in-one)           |

## Challenge 1: Wazuh Indexer Package Download Timeout (874 MB)

### Problem
During the indexer installation step, the `apt-get` process attempted to download the `wazuh-indexer` package (~874 MB) from `packages.wazuh.com`. The download consistently timed out after 15–20 minutes with the following error:

```
Err:1 https://packages.wazuh.com/4.x/apt stable/main amd64 wazuh-indexer amd64 4.14.5-1
Connection timed out [IP: 99.86.30.84 443]
E: Failed to fetch ... Connection timed out
```

### Symptoms
- Installation failed with `ERROR: Wazuh indexer installation failed`
- Script auto-cleaned the partial installation
- `ps aux` showed no active apt/wazuh processes after failure

### Root Cause
A combination of factors caused the timeout:
- **Jio's poor international peering** to AWS CloudFront (where Wazuh's package CDN is hosted), resulting in sustained download speeds of only 60–100 KB/s to international servers despite 100+ Mbps local speeds
- **McAfee network filter drivers** (pre-installed, expired subscription) actively intercepting and throttling all network traffic including VM traffic
- **ProtonVPN TAP adapter** installed in Windows, adding an additional network filter layer even when VPN was not actively connected

### Remediation
1. Uninstalled expired McAfee using the official MCPR removal tool
2. Uninstalled ProtonVPN from Windows to remove its TAP network filter driver
3. Restarted Windows to clear all network filter drivers from the stack
4. Re-ran the installation script during daytime hours to avoid peak congestion:
```bash
sudo bash wazuh-install.sh -a
```
5. Masked system sleep to prevent the VM from suspending mid-download:
```bash
systemctl mask sleep.target suspend.target
```
6. Monitored download progress via partial file size:
```bash
sudo ls -lh /var/cache/apt/archives/partial/
```

### Result
The indexer package downloaded successfully (~45 minutes total) and installed without errors:
```
INFO: Wazuh indexer installation finished.
INFO: wazuh-indexer service started.
INFO: Wazuh indexer cluster initialized.
```

## Challenge 2: APT Lock Conflict During Manager Installation

### Problem
Immediately after the indexer installed successfully, the script attempted to install the Wazuh manager but was blocked by an APT lock held by another process:

```
INFO: Another process is using APT. Waiting for it to release the lock. Next retry in 30 seconds (1/10)
...
INFO: Another process is using APT. Waiting for it to release the lock. Next retry in 30 seconds (7/10)
```

### Root Cause
Ubuntu's `unattended-upgrades` service had automatically triggered a background security update, acquiring the APT lock at the same time the Wazuh script needed it.

### Remediation
Stop the unattended-upgrades service before re-running the installer:
```bash
sudo systemctl stop unattended-upgrades
```

### Result
APT lock released, allowing the manager installation to proceed without conflict.

## Challenge 3: Install Script Unable to Resume Partial All-in-One Installation

### Problem
After the indexer was successfully installed but the script was interrupted (Ctrl+C) before the manager and dashboard could be installed, re-running `wazuh-install.sh -a` failed with:

```
ERROR: Wazuh indexer already installed.
INFO: If you want to overwrite the current installation, run this script adding the option -o/--overwrite.
```

The script has no native "resume" capability for all-in-one installs — it either installs everything fresh or errors out if any component already exists.

### Root Cause
The `wazuh-install.sh` script is designed for fresh deployments. It does not support resuming a partial all-in-one installation. The `-o/--overwrite` flag would wipe the existing indexer (including its data and configuration), requiring a full re-download of the 874 MB package.

### Remediation
Bypassed the install script entirely for the remaining components and installed them directly via apt:
```bash
# Install Wazuh Manager
sudo apt-get install wazuh-manager -y
sudo systemctl enable wazuh-manager
sudo systemctl start wazuh-manager

# Install Wazuh Dashboard
sudo apt-get install wazuh-dashboard -y
sudo systemctl enable wazuh-dashboard
sudo systemctl start wazuh-dashboard
```

### Result
Wazuh Manager and Dashboard installed successfully without disturbing the already-running indexer. All three components confirmed running:
```bash
sudo systemctl status wazuh-indexer wazuh-manager wazuh-dashboard
```

## Key Lessons Learned

- Disable or uninstall third-party network filter software (VPNs, antivirus with network drivers) before attempting large package downloads in a VM
- Mask system sleep when running long downloads overnight to prevent interruption
- Monitor `/var/cache/apt/archives/partial/` to track active download progress
- The `wazuh-install.sh` script does not support resuming — if interrupted after partial install, use direct `apt-get install` for remaining components rather than re-running the full script with `--overwrite`
- Jio's international download speeds to AWS/European endpoints can be significantly lower than local speedtest results suggest — plan for longer download times accordingly
